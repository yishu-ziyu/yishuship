# yishuship 各环节对照业界标准（2026-09-26）

用业界公认最好的做法对照 yishuship 的每个环节。参考资料只作参考，不当规格：只有能解决我们真实遇到过的问题、或者一旦发生就代价很高的问题，才吸收进来。

## 结论

| 环节 | 对照谁 | 我们现在 | 差距 |
|---|---|---|---|
| 1 值不值得做 | Cagan、Torres、Shape Up | 问清为谁和问题、查已有产品、挑战一次、做 / 缩小 / 不做 | **大**：没问愿意花多少、没写明不做什么、没点出最危险的假设 |
| 2 行为怎么写 | Example Mapping、Anthropic 长任务文章 | `用户做什么 → 看到什么` | **小**：评估显示 9 次里 9 次已带真实数据的例子（原判断为「中」，被数据推翻） |
| 3 第一块怎么切 | 纵向切片（Humanizing Work） | 最薄的端到端、能单独成立 | 一致，不改 |
| 4 停下来问 | 单向门 / 双向门 | 只问用户看得见的、难以撤回的 | 一致，不改 |
| 5 做和验证 | Claude Code 最佳实践、Anthropic 长任务文章 | 同一个会话自己做、自己验、自己报告 | **大**：没有独立检查；开工前不先确认产品还好着 |
| 6 做完和上线 | Shape Up | 上线标准 + 以新用户身份再装一遍 | **小**：判断够不够好时，没和用户现在的处境比 |
| 7 上线之后 | Google HEART、Torres | 成形时 8/9 次已写「怎样算做对了」，但上线后没人回头看 | **大**：信号写了，没人去看 |
| 8 技能本身的质量 | Anthropic 技能写法指南 | 2026-09-27：13 个场景、和不装插件比、沙箱隔离运行（`evals/`） | 已补上 |

### 2026-09-28：对照「软件工程闭环」补两处

对照一份讲「需求 → 设计 → 任务 → 开发 → 测试 → 上线 → 观测 → 新需求」闭环的教程，缺的是测试里的「之前的功能还能用」和观测里的「上线后从哪看出来」。每个场景各跑 2–3 次，只跑装了插件的一侧：

| | 改前 | 改后 |
|---|---|---|
| 成形时写明上线后从哪看出来 | 0 / 2 | 3 / 3 |
| 做下一块时重跑上一块的复查，并如实说明 | 1 / 3 | 2 / 3 |
| 回头看时先查信号、报数字再问 | 2 / 2 | 未改（已经会做，这条规则没加） |
| 继续做一块（continue-build）核心 / 目标 | 1.00 / 0.75 | 1.00 / 0.75 |

第二步补项目这一层：每个项目一份 `.ship/PROJECT.md`。上半由 Agent 写（这是什么、怎么搭的、界面截图），下半由 `ideas.py --project` 从想法文件生成（现在能做什么和它的复查、所有想法、没处理的遗留）。想法文件分成意图 / 设计 / 任务三区。全套 14 个场景各跑 2 次：

| | 结果 |
|---|---|
| 做完一块后，项目文件列出新行为和它的复查 | 2 / 2 |
| 项目文件列出范围外的导出 bug | 2 / 2 |
| 项目文件的手写部分填好、截图文件都在 | 2 / 2 |
| 成形时项目文件写对了这是什么、怎么搭的 | 2 / 2 |

全套里有三个场景的核心分下降。用改动前的版本各跑 3 次对比：natural-vague 0.67 → 1.00，continue-switch 0.83 → 1.00，start-new-project 0.89 → 0.89。这三个场景在旧版上本来就不稳定。natural-vague 的真实问题是先问一轮再建文件，问题只存在聊天里；现在规定每问一轮之前先把已知的写进进度文件。

复查那条剩下的失败，是把旧检查失败归因成测试数据被共用，场景本身也确实有这个毛病（旧检查读的是真实的 todos.json）。

一处更正：曾判断「完成报告的『改之前』不属实」，核实后是评分标准只认「会话开始时」一种理解；报告实际取了「这一块之前」的旧代码运行过，属实。

## 逐项

### 1 值不值得做

- **Cagan**：四大风险里最难的是价值风险（用户到底要不要），要最先处理。[SVPG](https://www.svpg.com/four-big-risks/)
- **Torres**：只测「最要命、证据又最少」的假设，而且越具体越好测。[Product Talk](https://www.producttalk.org/2023/10/assumption-testing/)
- **Shape Up**：
  - 先定「愿意花多少」再设计：「估算从设计出发得到一个数字，愿意花多少从一个数字出发得到设计。」[第 3 章](https://basecamp.com/shapeup/1.2-chapter-03)
  - 警惕「2.0」式的大杂烩项目。[第 3 章](https://basecamp.com/shapeup/1.2-chapter-03)
  - 写明不做什么（no-gos）和容易掉进去的坑（rabbit holes）；问题最好用「一个具体的故事说明现状哪里不行」来定义。[第 6 章](https://basecamp.com/shapeup/1.5-chapter-06)

**我们的真实证据**：vibereader 的「让 VibeReader 的交互体验更好」就是一个大杂烩式标题，至今有 4 个问题在等决定。旧版时 vibereader 的一个任务拖了两个月。

**改法**：成形时多写三行：
- 愿意花多少（几块、几天）
- 这次不做什么
- 最危险的一个假设，以及最便宜的验证办法

超出「愿意花多少」时，停下来问你要不要继续，而不是自动延长。

### 2 行为怎么写

- **Example Mapping**：规则下面挂具体例子，答不上的记成问题。问题太多说明还没准备好，规则太多说明该拆了。[Cucumber](https://cucumber.io/blog/bdd/example-mapping-introduction/)
- **Anthropic**：每个功能写成端到端描述，附验证步骤，初始都标为「未通过」，只有认真测过才改成通过；新会话读这份清单挑下一个。[Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**改法**：每条行为下至少一个用真实数据写的例子，比如「点《xx》回答里的 [3] → 第 12 页『……』那句高亮」。这个例子同时是这一块的验收标准、下次会话的回归检查，也是技能评估的素材。

**不采纳**：Anthropic 发现 JSON 比 Markdown 更不容易被模型乱改。但进度文件要给人读，我们也还没见过被乱改的情况，所以先不换格式，观察后再说。

### 5 做和验证

- **Claude Code 最佳实践**：「做事的智能体不该同时给自己打分」，在算作完成之前，让一个全新上下文的检查者只看改动和验收标准。检查者只报影响正确性或需求的差距，避免过度修补。[Claude Code 文档](https://code.claude.com/docs/en/best-practices)
- **Anthropic**：每次开工先把应用跑起来，做一次基本的端到端检查，确认上次没留下坏掉的状态，再做新功能。[Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**我们的真实证据**：2026-09-26 移动仓库后，我说状态行「验证通过」，但测的是带引号的路径，不是配置里的真实命令，结果状态行坏了一个多小时才被发现。这正是自己给自己打分出的错。

**改法**：
- 报告「完成」前，派一个全新上下文的检查者，拿第 2 项的例子逐条核对，只报不符合的地方。
- 每次开工先跑一遍上一块的例子。

### 6 做完和上线

- **Shape Up**：判断「够不够好」时，跟用户现在的处境比，而不是跟理想状态比。[第 14 章](https://basecamp.com/shapeup/3.5-chapter-14)

**我们的真实证据**：2026-09-26 发布 3.5.0 时，推送之后以新用户身份克隆，才发现默认分支还是 v2。「以新用户身份再走一遍」这条规则是有效的，保留。

**改法**：上线决定题里加一行「和现在相比好在哪」。

### 7 上线之后

- **Google HEART**：先定目标，再找能观察到的信号，最后才定指标。[Google Research](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/)

HEART 是为大规模产品设计的，对一个人做的产品来说太重，只取「目标 → 能观察到的信号」这一半。

**改法**：
- 成形时写一行「怎样算做对了」，写成一个能观察到的用户行为。
- 上线一段时间后，`/yishuship` 提醒你回头看，然后问：继续做、就此打住，还是砍掉。

### 8 技能本身的质量

- **Anthropic 技能写法指南**：先写评估再写技能；至少 3 个场景；先测不装技能时的表现作为基线；用一个全新会话做真实任务，观察它哪里出错，再回来改。[Claude 文档](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices)
- 本机 Claude Code 自带 `claude plugin eval`，会自动对比装和不装插件的得分差异。注意它默认把报告发布到 claude.ai，要加 `--no-publish`。
- **OpenAI harness engineering**：出问题时不让模型「再努力」，而是问缺了什么能力，把它做成看得见、能被程序检查的东西。[OpenAI](https://openai.com/index/harness-engineering/)（原文未能读到，只见到搜索摘要，作旁证。）

**改法**：
- 建 `evals/`，每一步（成形、继续、再问一遍、总览）至少 3 个场景，用真实的想法做素材。
- 评分只看能观察到的行为，比如「没写代码就停下来问了」「问题只涉及用户看得见的东西」「给了真实来源」「说完成时有改之前和改之后」。
- 每次发布前跑一遍，并和不装插件的基线比较。

## 看过但不采纳

| 做法 | 为什么不采纳 |
|---|---|
| Shape Up 的山形图 | 一个人的项目，看「做完几块」已经够用 |
| 每次比较三个方案（Torres） | 会加重你的决定负担；「做 / 缩小 / 不做」已经覆盖主要选择 |
| 亚马逊先写新闻稿（PR/FAQ） | 用户看得见的行为已经用产品语言写了，再写一份是重复 |
| 用 Stop 钩子强制检查 | 和 yishuship「不设拦截」的原则冲突；用独立检查者代替 |
| HEART 的完整指标体系 | 太重，只取「目标 → 信号」 |
